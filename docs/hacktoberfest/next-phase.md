# Next phase: a launch pack people want to share

Product roadmap and evaluation checkpoint. The participant later reported five hours until evaluation. Automatic publication is outside scope; paid generation remains an explicit selected-project action.

## Product promise

**Turn your GitHub project into a launch people understand.**

One entry point, one reviewed brief, one downloadable pack. Internally this still needs several checks; the user should not have to manage a collection of tool panels. A draft reel should explain the problem, demonstrate the actual product when footage is supplied, and ask for one clear action.

The current foundation works locally: repo-first selectable model analysis, deeper readiness handoff, two positioning stories, launch posts, GitHub OAuth/private support awaiting account configuration, approved deployed-site recording, and a 25s Brag-inspired portrait/landscape promo with live ElevenLabs aligned voice/captions and optional music. Broader research, batch automation and hosting remain separate priorities.

## After the hackathon

1. **Public beta:** authenticated accounts, durable jobs/artifacts, encrypted per-user keys, read-only selected-repository GitHub App, deletion/expiry, rate/quota controls and worker isolation. Preserve local/BYOK open-source use. GPL-3.0-only is selected; retain third-party attribution and document contribution/setup clearly.
2. **Brand memory:** save audience, tone, CTA, examples and actual product claims so future releases stay coherent. Never fabricate testimonials or traction.
3. **Release-to-launch:** compare revisions or release notes, then draft “what changed” assets with owner review. This gives developers a recurring reason to return.
4. **Launch experiments:** offer a few hooks and a small owner-published sequence, record actual results, and suggest the next experiment. Add channel integrations only when there is demand and platform support.
5. **Research:** integrate bounded Agent-Reach sources with attribution, freshness and uncertainty. Don’t claim comprehensive competitor coverage or originality.

## Distribution and measures

Start with student/solo developers who already built something and struggle to explain it. Publish Sudo's own launch reel, show the actual before/after output, and invite the first 10 developers to try their own repos. A small optional “Made with Sudo Launch” credit can link back; allow removal and do not publish private project pages automatically.

Measure repo-to-first-export completion/time, factual edits required, repeat use for another release, and whether people actually share or use the output. Views alone do not establish product value, and no feature can guarantee virality.

Local/BYOK can remain open source; a hosted service can charge for convenience, rendering and storage after usage/costs are understood. Validate usefulness before building subscriptions or a social scheduler.
